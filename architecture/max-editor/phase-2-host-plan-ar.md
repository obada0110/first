# من النموذج إلى الدمج المراجع — خطة MAX EDITOR

## من يملك القرار الآن؟

| السطح المدروس | نقطة الوصل المختبرة | ما لا ينتقل إلى النواة |

| Android: `SingleScreen` ← `SourceTimeline`، `MainActivity.configureFlutterEngine` و`SingleChannel` | زر K في **بناء المختبر فقط** يفتح مسار Flutter يستخدم SourceTimeline الحقيقي والقالب والخط الموجودين. يختار المستخدم المقطع ويحرك المؤشر؛ قناة خلفية منفصلة توصل أمر JSON إلى JAR النواة، وتعيد نتيجة تُحدّث الشريط. | الشاشة العادية، مسار SAF والحفظ `single-v1.json`، منح القراءة، ExoPlayer وPlayerView وMedia3 Transformer. لا نرسل مشروعًا مركبًا إلى كود يفترض `clips.single()`. |

مخطط v1 والمراجعة مستقلان عن `api:2`. المدخل `{api,method,data}`. `open` يأخذ النص الخام، `snapshot` يعطي النص الكامل، `edit` يقبل أمرًا ومراجعة متوقعة، `render` يرد بمواصفة أو null. الرد `{api,ok,revision,value,error}`؛ الفشل لا يحرّك مؤشر التاريخ. `addClip` يأخذ كائن مقطع كاملًا بمعرّف جديد وassetId مسجّل: لا يفتح ملفًا ولا ينشئ أصلًا ضمنيًا. `delete` يستهدف ID، `split` يستقبل rightId جديدًا، وtrim يأخذ زمن المشروع بالميكروثانية. `order` يتطلب تبديل كل IDs الطبقات. المنصة لا تعيد حساب القطع ولا تخمّن نجاحه. `STALE_REVISION` يستدعي قراءة ثم قرارًا جديدًا وليس إعادة آلية للأمر. `DUPLICATE_ID` و`MISSING_ASSET` خطأ بيانات، و`UNDO_EMPTY` يعني عدم توفر الأمر. الإقرار في الذاكرة **ليس** إقرار حفظ دائم.

سجل Undo/Redo واحد لكل جلسة في النواة، لا سجلّان داخل adapter والنواة. يزيد رقم المراجعة حتى عند التراجع؛ تعديل جديد يمحو redo، وإعادة فتح اللقطة تبدأ تاريخًا جديدًا. لا تنقل الهوية من `index` أو `URI`: لحظة الإضافة فقط يولّد العميل ID آمنًا وفق v1 ويحتفظ به عبر المحاولة والحفظ والنقل. استُخدمت IDs حتمية في العينة لتسهيل مقارنة كل حقل. المعرّف الدائم للأصل ليس المقبض العددي الذي ينشئه `register()` بعد استعادة Blob.

## الوسائط والحفظ

- **الآن:** مخزن IndexedDB تجريبي جديد للوثيقة وبيانات الأصلين الاصطناعيين حسب `assetId`؛ يعاد إنشاء File والمقبض محليًا. حتى قاعدة fallback في النسخة المعزولة لها اسم مختلف. Android يكتب عبر `AtomicFile` في `filesDir/pilot-v2.json` بحزمة `lab.maxeditor.hostpilot`. لا تنتقل ذاكرة التاريخ أو URI أو البايتات بالفحص الدائري؛ المنتقل هو مشروع v1. مسار Flutter يعرض هندسة الشريط وليس فيديو مركبًا.
- **لاحقًا:** مخزن ربط محلي منفصل على Android: `assetId → URI + persisted read permission + digest/size/type`. على الويب `assetId → blob/ref + digest`. إذا فُقد أصل أو مُنعت قراءته، يُظهر الاسم والحالة ويطلب إعادة ربط صريحة؛ لا مطابقة بالاسم وحده ولا إسقاط للطبقة. افحص حزمة الوارد والبصمات وحدود الحجم/العمق في staging، ثم انشر الروابط واللقطة بصورة ذرية أو أبقِ السابقة. FX غير مدعوم يُحفظ مدخله الأصلي ويُنبّه المستخدم؛ لا إنتاج لملف ناقص. لا يقدّم المختبر محوّل legacy أو حزمة تبادل وسائط.

## المعاينة والتصدير: محركان فعليان يستهلكان قرارًا واحدًا

1. تحدد النواة `frameIndex → ptsUs` حسب معدل كسري، موقع المصدر والنطاق نصف المفتوح، ومواصفات كل طبقة نشطة بالترتيب الخلفي–الأمامي. حساب transform والخطوط الزمنية للمفاتيح في النواة (زمن الفيديو للأصل وزمن الطبقة محلي) مع اختبار أول/آخر إطار. RenderSpec **ليس** decoder أو shader أو encoder. في هذه التجربة لا يزال الرسم القديم للويب يقيّم العرض؛ تبديله خطوة مستقلة.
2. **الويب:** أبقِ `HTMLVideoElement`/فك الترميز، Canvas 2D/WebGL و`effects.js`، مع `requestVideoFrameCallback` عند توفره لمواءمة إطار المعاينة لا لتحديد وقت المشروع. يرسم compositor الخلفية ثم الفيديو الأساسي وFX ثم تحويلاته والطبقات وأخيرًا النص حسب ترتيب المشروع. لا تحذف المسار الحالي المبني على `captureStream/MediaRecorder`. لمسار تصدير ثابت الإطارات مستقبلاً اختبر WebCodecs + muxer مع تَحقُّق encoder/codec فعلي؛ يُعلَن fallback وترميزه/حاويته صراحة.
3. **Android:** في المعاينة يبدأ adapter بربط ExoPlayer/MediaCodec بكل فيديو **ظاهر**، وحد أقصى معلن لفك متزامن. SurfaceTexture → OpenGL ES/EGL framebuffer للمزج والتحويل وقصّ الحواف، ثم EGL surface إلى PlayerView/سطح العرض. يستخدم التصدير نفس الـcompositor والرسم إلى input surface لـMediaCodec؛ mux للصوت والفيديو بـMediaMuxer. يمكن استخدام Media3 Composition/Transformer ومؤثر GL مخصص إذا اجتاز اختبارات الترتيب والتوقيت؛ لا يكفي إلحاق مقاطع بالتتابع كي يصبح التصدير متعدد الطبقات. احترم دوران المصدر ونسبة العرض واللون وalpha.
4. **المؤثرات:** المرجع الفعلي ذو الترتيب الثابت `key → blur → motion → temp → light → contrast → sat → glow → rain → frost`. ثبّت IDs ومفاتيح المعاملات والمدى والافتراضيات وزمن الحركة وعينات المصدر في كل pass، بما فيها المؤثرات التي تعيد أخذ عينات بعد chroma key. ابدأ بمؤثر واحد مع golden frames ثم التركيبات والحدود قبل نقل التالي. اختبر المعاينة وتعطيل/إزالة FX والـsplit والحفظ، وافك ترميز التصدير لمقارنة صور وصوت، مع مقاييس تسامح معلنة لإعادة الضغط.
5. **النص والصوت:** النص في Android يُشكَّل بـStaticLayout/Canvas ثم texture، وفي الويب Canvas مع اتجاه RTL متفق عليه، محاذاة، line breaks، outline/shadow ومقاييس الخط. لا تغيّر Tajawal أو تصميم الواجهة. الصوت منفصل عن رسوم الفيديو: WebAudio graph حاليًا، وAndroid يفك PCM ثم resample/mix حسب الجدول ثم AAC. سياسة v1 الحالية صوت الأصل إن وُجد والـoverlay مكتوم؛ أي تمكين لمسارات صوت إضافية يحتاج عقدًا وقدرات واختبارات مستقلة (نغمتان، كتم، قص، تزامن، نهاية دون حشو). لا ادّعاء بأن v1 يحتوي mixer لم يُبنَ.
6. **اختبار الإطار الأسود:** افصل براهين `state.restore` عن `pixels.visible`. سجّل عمر Surface/ترتيب attach و`prepare/seekTo` و`onRenderedFirstFrame` وزمن الصورة والاتجاه. انتظر surface صالحًا واطلب إعادة تقديم الموضع الموقوف عند الحاجة؛ لا تُمثّل الإصلاح بتشغيل الفيديو خلسة أو بصورة ثابتة زخرفية. كرّر pause→restore→rotate→seek→play مع عينة ملونة وفحص المركز داخل الفيديو ثم مع لقطة أصل سوداء فعلًا لمقاومة الإيجابيات الكاذبة. لا تعتمد الإصلاح قبل هاتف فعلي.
